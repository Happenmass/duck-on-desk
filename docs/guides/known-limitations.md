# Known Limitations

[Back to README](../../README.md)

| Limitation | Details |
|---|---|
| **Codex CLI: terminal focus is best-effort** | `request_user_input` cards can jump back to a local Codex session when its official-hook/session metadata identifies a focus target. JSONL alone may not carry a usable terminal PID; in those cases the card remains a read-only reminder. |
| **Codex CLI: partial hook coverage** | Official hooks cover live state and `PermissionRequest` observation/intercept mode, but not every runtime signal. Duck keeps JSONL polling active for hook-disabled sessions and fallback-only events such as web search, compaction, and aborted turns, so those state/metadata events can still have polling latency. Approval prompts are not inferred from JSONL; they require official `PermissionRequest` hooks. |
| **Codex CLI: user-input cards are read-only** | Codex does not expose `request_user_input` through the official hook event set. Duck observes the JSONL transcript, so the reminder can arrive after the polling interval. Choices and free-form answers stay in Codex's native UI; Duck neither injects keystrokes nor turns these questions into actionable approvals. |
| **Custom HTTP agents: state-only, sender required** | Registering an executable assigns an ID and exposes the `/state` contract; it does not install a hook, watch the process, or prove the application is an AI tool. The application or an adapter must send events using the current port from `~/.duck-on-desk/runtime.json`. Custom agents cannot use `/permission` in v1, so approval stays in the application's native UI. |
| **opencode: child sessions are background-only** | When opencode emits `session.created` with `event.properties.info.parentID`, Duck treats that child/subtask as headless background work owned by the root session. It is hidden from HUD/focus surfaces and does not contribute to multi-session fanout animations. |
| **opencode: terminal focus limited to spawning terminal** | The plugin runs in-process with opencode, so `source_pid` points to the terminal that launched opencode. If you use `opencode attach` from a different window, terminal focus jumps to the original launcher. |
| **Orca: terminal focus is not supported on Linux** | Orca hosts its terminals in a detached `orca-terminal-daemon` whose own parent has already exited, so `Orca.exe` never appears in the agent's process tree and no window title carries the project path — neither of Duck's usual strategies can find it. Focus instead uses `ORCA_PANE_KEY` from the environment plus Orca's own CLI (`orca terminal switch`), and requires the `orca` CLI: `PATH` first, then `%LOCALAPPDATA%\Programs\orca` on Windows and `/usr/local/bin/orca` or `~/.local/bin/orca` on macOS, because an app launched from Finder inherits none of the shell's `PATH`. Windows raises the window from the focus script; macOS activates the `Orca.app` bundle by absolute path (`/Applications` then `~/Applications`) after the pane switch succeeds, and reports `orca-app-not-found` if it is installed anywhere else. **Linux is unsupported**: the only by-name handle is WM_CLASS `orca`, which is a substring match that also hits GNOME's Orca screen reader and OrcaSlicer, so a miss would activate an unrelated window and report success. There, an Orca-hosted session falls back to the normal process-tree behavior, which cannot resolve the daemon. |
| **Orca: a terminal that advertises nothing can be mistaken for the pane** | The pane key is trusted only when Orca is the innermost terminal, which is decided from environment markers (`WT_SESSION`, `ConEmuPID`, `KONSOLE_VERSION`, the multiplexers `TMUX` / `STY` / `ZELLIJ`, and others). A terminal that sets no marker of its own — a bare `conhost` or `pwsh` window — started *from* an Orca pane inherits `TERM_PROGRAM=Orca` and the pane key, so Duck raises Orca and reports a successful focus while the window the agent really lives in is never found. |
| **Orca on Windows: the first focus of a session can land on the wrong tab** | The window raise runs inside the generated focus script and is immediate, but the pane switch needs an `orca` CLI round-trip, and the first focus for a session pays a cold `terminal list` before its `terminal switch`. A cold CLI has been measured exceeding the 6 s timeout: the call is then killed (`orca-cli-timeout` in `focus-debug.log`) with Orca already in front, showing whichever tab was last active, and no switch happens at all. Clicking again works — the second attempt meets a warm CLI, and once the handle is cached the steady state is ~0.5 s. |
| **Orca on macOS: nothing comes forward when the pane is gone** | The generic macOS raise is suppressed for an Orca-hosted session, because it derives its target from the daemon's process path and would activate `Orca.app` before the pane switch has said which tab — or whether the pane still exists. `open` also *launches* Orca, and the terminal daemon outlives its window, so a session whose window has been closed would cold-start the IDE on a click. The pane switch therefore owns the raise, and if it fails nothing is activated at all: clicking the pet appears to do nothing, with the reason recorded in `focus-debug.log`. |
| **Orca: two or more Orca windows cannot be told apart** | The entire window title is `Orca`, with no project path to match on, so with more than one window open Duck refuses to guess and raises nothing (`orca-window-ambiguous` in `focus-debug.log`). The tab switch still runs, so the correct pane comes forward inside a window that stays behind. Use a single Orca window for reliable click-to-focus. |
| **Orca on macOS: CLI lookup includes Homebrew and the app bundle** | In addition to `PATH`, `/usr/local/bin/orca`, and `~/.local/bin/orca`, Duck checks Apple Silicon Homebrew at `/opt/homebrew/bin/orca` and the CLI bundled under `/Applications/Orca.app` or `~/Applications/Orca.app`. This is required for Finder-launched Duck instances whose inherited `PATH` omits Homebrew. |
| **Pi: state-only integration** | Duck observes Pi interactive-session lifecycle and tool events through a global extension, but does not intercept permissions or add confirmation prompts. Pi keeps its default YOLO execution behavior. |
| **Pi: session reload may briefly flicker** | Pi emits `session_shutdown` during reload/session replacement, then `session_start` for the new runtime. Duck may briefly remove and recreate the Pi session. |
| **Windows Terminal: tab focus is limited** | Windows Terminal exposes one host window/process for multiple tabs, so Duck cannot reliably activate a specific tab. HUD/Dashboard focus works best with separate classic `cmd.exe`/PowerShell windows, or with separate Windows Terminal windows whose title contains the project folder name. On Windows 11, `cmd.exe` and PowerShell may be hosted by Windows Terminal unless the default terminal application is set to Windows Console Host. **v0.12.0 and earlier only**: when Windows Terminal is the OS default terminal app, every prompt submission also briefly flashed a console window (#627) — WT's console delegation doesn't always honor `CREATE_NO_WINDOW` on the hook's PowerShell snapshot, and switching the default terminal app to Windows Console Host was the workaround for that too. **v0.13.0** samples the foreground window from Duck's own process instead (no subprocess spawn on that path), so the flash is fixed and this workaround is no longer needed there. |
| **Windows: hook process metadata needs Duck running** | Terminal focus and session PIDs come from a process-tree lookup that the hook only performs while Duck is actually running. From **v0.13.0**, after you quit Duck, a leftover CLI hook no longer inspects the process tree at all — it posts what it has and stops. The visible effect is that a session started while Duck was closed has no click-to-focus target until its next event with Duck running; a session Duck already knows keeps the PID it learned. The same applies for a few seconds after Duck is force-killed, and whenever `~/.duck-on-desk/runtime.json` is unreadable (Doctor → Local server warns). Until you restart Duck once on v0.13.0, the pre-v0.13.0 `runtime.json` has no owner field, so hooks treat Duck as offline and omit this metadata — a single restart fixes it. |
| **Windows: some agents still run a PowerShell process lookup while Duck is online** | The lookup above is still a hidden PowerShell that reads the process list, and security software may flag it. **v0.13.0** removes it when Duck is not running, and no longer stores the agent's command line in the temporary cache (only a `headless` yes/no). The online path is unchanged for now — tracked in [#681](https://github.com/rullerzhou-afk/duck-on-desk/issues/681), [#627](https://github.com/rullerzhou-afk/duck-on-desk/issues/627) and [#634](https://github.com/rullerzhou-afk/duck-on-desk/issues/634). |
| **macOS packaged auto-update needs a one-time bridge install** | Builds from before the macOS in-app updater contain no ZIP update payload and cannot update themselves. Existing users must manually install the first signed bridge DMG once. After that, later signed/notarized releases can be downloaded in Duck and installed with **Restart Now**, or after choosing **Later** and quitting/reopening the app. Unit and package checks do not replace a real signed A→B device upgrade; any platform not yet covered by that matrix must stay marked pending in release evidence. |
| **Linux packages do not auto-update** | AppImage/deb installs still require a manual download from GitHub Releases. A `git clone` + `npm start` checkout can update through the in-app `git pull` path. |
| **Linux/Wayland: limited dragging & cursor tracking** | Native Wayland forbids client-side window positioning and global cursor queries, so under a Wayland session the pet spawns centered, can't be dragged, and has no mouse tracking. On a Wayland session with an X server available, Duck relaunches itself once under XWayland (`--ozone-platform=x11`) — Electron fixes the Ozone backend in C++ before any app code runs, so an in-process switch is too late — which restores window positioning and dragging; cursor tracking is then limited to the pet's own surfaces. Full-screen cursor tracking is **not** achievable under Wayland for an ordinary app — use a native X11 (Xorg) login session for that. `DUCK_OZONE_PLATFORM` controls the automatic relaunch: `x11` forces the XWayland relaunch, `wayland`/`auto` keep the native-Wayland default; an explicit `--ozone-platform=…` you pass on the command line is always honored as-is. See [#441](https://github.com/rullerzhou-afk/duck-on-desk/issues/441). |
| **No test framework for Electron** | Unit tests cover agents and log polling, but the Electron main process (state machine, windows, tray) has no automated tests. |
| **Claude Code: tools rejected when Duck is offline** | When Duck's HTTP server isn't running, the `PermissionRequest` hook (registered by Duck) fails with `ECONNREFUSED`, and Claude Code currently denies the tool call instead of falling through to its built-in prompt — affecting `Edit`, `Write`, `Bash`, etc. This contradicts CC's documented non-blocking behavior for HTTP hook failures — see [anthropics/claude-code#46193](https://github.com/anthropics/claude-code/issues/46193). Workaround: keep Duck running (recommended), or temporarily rename the `PermissionRequest` key in `~/.claude/settings.json` to disable the hook. |
| **Claude Code + CC Switch: protected auto-repair pause** | Duck normally re-registers Claude hooks when another tool rewrites `~/.claude/settings.json`. If the file suddenly shrinks enough to look unsafe, Duck pauses automatic repair to avoid preserving a partially rewritten config and Doctor reports Claude Code as needing Fix. Use **Settings -> Doctor -> Fix**, restart Duck, or re-enable automatic Claude hook management to repair. CC Switch's Shared Config Snippet can carry Duck hooks on the same machine, but those hooks include local paths and ports, so do not treat them as a cross-device snippet. |
